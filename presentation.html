🔒 Production Data Warehouse Standards PostgreSQL vs SQLite
  • Why SQLite Was Banned: SQLite lacks row-level locking, concurrent writes, and production ANSI SQL capabilities.
  • Composite Unique Grain Constraint:
    CONSTRAINT uq_fact_grain UNIQUE (track_sk, genre_sk, time_sk, category_sk)
  • Surrogate Keys: Pure SERIAL autoincrementing integers decoupled from operational source natural keys.
  • Special Dimension Keys: Default SK = 0 inserted for non-awarded catalog tracks, avoiding NULL foreign keys.

Section 10.2 • Technical Understanding

Evaluator Defense Cheatsheet & Trap Q&A

Interactive answers to the 6 most challenging questions evaluators ask during the defense.

Rubric: Sec 10.2 Q&A Defense (0.25 pts)
1. Why is SQLite strictly prohibited and PostgreSQL required? ▼
Answer: SQLite is an embedded file database lacking multi-user concurrent write locking, client-server isolation, and advanced ANSI SQL capabilities like concurrent upserts (ON CONFLICT DO UPDATE with partial indices). PostgreSQL provides true production-grade transactional integrity and ACID guarantees.
2. Why did you assign retries=0 to data validation tasks? ▼
Answer: Data quality violations are deterministic. If a dataset has an invalid year (1800), re-evaluating it 3 times without modifying the source will reproduce the exact same failure 3 times, wasting compute and delaying failure alerting. Only transient operational errors (network latency, socket disconnections) warrant retries.
3. Why is passing Pandas DataFrames through Airflow XCom an anti-pattern? ▼
Answer: Airflow XCom serializes data into the Airflow metadata database (PostgreSQL), which is designed for tiny coordination messages, not multi-megabyte datasets. Storing 114,000 rows in XCom causes metadata bloat, latency, and memory exhaustion. We pass Parquet file paths and lightweight metadata dictionaries.
4. How does your pipeline guarantee 100% idempotency upon re-execution? ▼
Answer: Idempotency is enforced by a composite natural grain constraint on the fact table (track_sk, genre_sk, time_sk, category_sk) paired with an atomic PostgreSQL INSERT ... ON CONFLICT DO UPDATE. Running the exact same batch 10 times results in zero duplicate rows and zero metric inflation.
5. How did you reconcile multi-artist collaborations with Spotify track records? ▼
Answer: We normalized artist credits by tokenizing on delimiters (; in Spotify; featuring, &, with in Grammys) to extract the primary canonical artist for cross-source matching, while preserving the full collaboration string in dim_track.
6. What happened to the 99.5% of songs in Spotify that never won a Grammy? ▼
Answer: They are preserved in the Data Warehouse via Left Outer Join semantics with is_grammy_winner = FALSE and foreign keys mapped to surrogate key 0 (category_sk = 0: "Not Applicable"). This allows analytical queries to compare winners against the baseline catalog.
