Why both sources

Spotify has sound, popularity and genre but no recognition. The Grammys have recognition and year but no audio or consumption data. Every KPI combines one attribute from each source.

Scope

Batch, manually triggered; exact matching on a normalized key; association, not causation (popularity is one snapshot).

Traceability IDs

RQ-xx → DQ-* rules → TR-xx transformations → DW views → KPI-xx, used consistently in code, docs and evidence.

The brief asks for requirements before profiling and modelling. Each requirement determines the data, rules, transformations and dimensional structures.

Point at the source columns: no row can be answered with a single source, which is what justifies the integration.

If asked “why no nominees?”: the Grammy file only contains winners (4,810 of 4,810 have winner = True). So we compare winners vs catalog and document it as a limitation.

Source preparation ≠ ETL load

The source-seed service loads the provided Grammy CSV into PostgreSQL and reconciles it (4,810 = 4,810 rows). The DAG then extracts only from the database.

# dags/reliable_music_pipeline.py (dependencies)
from airflow.sdk import dag, task, get_current_context

s_val = validate_spotify_raw_task(extract_spotify_task())
g_val = validate_grammys_raw_task(extract_grammys_task())
prep  = validate_prepared_task(
          transform_and_integrate_task(s_val, g_val))
load_dw_task(prep)

Follow the diagram left to right. The two branches are independent and observable: each has its own extraction and its own gate.

The convergence is the key point: with the default all_success rule, transformation cannot start if either raw gate fails, and load_dw cannot start if the prepared gate fails.

Logic lives in src/; the DAG only describes the flow. XCom only carries paths and small dicts.

Severity policy

Critical → CriticalDataQualityError: task fails, downstream upstream_failed, DW untouched

Warning → logged + recorded, CONTINUE_WITH_WARNING

Info → recorded as a trend signal, never blocks

A threshold is a decision

Duration ≥ 99.9%: one corrupted row is tolerated (TR-01 removes it), but a systemic unit change (> 114 rows) stops the batch.

18 rules, well above the minimum of six. We did not force symmetry per dataset: coverage follows the risks and the requirements.

Explain one rule of each severity. The duration rule shows how a threshold is justified: it is not chosen so that the current batch passes, but to tolerate isolated corruption and stop a systematic error.

Prepared-layer rules check post-transformation invariants (ranges with no tolerance, unique grain) and integration integrity, including a minimum match rate.

Trap: “Do you change data so validation passes?” No. Validation detects; transformation applies rules that are justified on their own (TR-xx).

The highest-weighted criterion (0.90). The core idea: a retry only makes sense when another attempt can succeed without changing the input or the code.

That is why extraction and the load retry, while the gates and the transformation do not. Test D proves the first case; Tests B and E prove the second.

For observability, walk the five questions of the brief: what ran, when, did it succeed, where and why it failed, and what happened next.

If asked “why only one retry for the load?”: it is the heaviest task. One retry covers a short lock; if it fails again the problem is no longer transient.

-- strategy: snapshot load in ONE transaction
CONSTRAINT uq_fact_grain UNIQUE (track_sk, genre_sk, time_sk, category_sk)

INSERT INTO fact_music_performance (...) SELECT ...
ON CONFLICT (track_sk, genre_sk, time_sk, category_sk)
DO UPDATE SET popularity = EXCLUDED.popularity, ...,
              batch_id = EXCLUDED.batch_id
RETURNING (xmax = 0) AS inserted;      -- inserted vs updated

DELETE FROM fact_music_performance
 WHERE batch_id <> :run_id;            -- stale rows of older snapshots
-- rows written ≠ prepared rows  →  RuntimeError → ROLLBACK

Why upsert + purge (not upsert alone)

If a track changes from unmatched to matched, its grain key changes. An upsert alone would keep the old row next to the new one. The purge removes rows that are not in the current snapshot.

Partial or failed runs

Dimensions and facts share one engine.begin() transaction: any error rolls everything back and the previous snapshot stays. A failure before the load (Test B) never touches the DW.

The brief asks for four things: the strategy, the keys or load logic, a before/after comparison, and what happens after a partial run. Go in that order.

Read the key line: 0 inserted, 113,549 updated, 0 purged. All measures are identical; only batch_id changes.

If asked “why not truncate-and-load?”: also valid. We chose upsert + purge in one transaction because readers never see an empty table and we can count inserts and updates as evidence.

Why this is Critical

Below about 114 matched rows, KPI-02 has no genre with n ≥ 5 and KPI-01 compares the catalog against a handful of songs. A 4× drop from the usual 0.42% means the match key broke, not that the music changed.

What the test taught us

The first time we ran it, the gate only required “at least one match” and the degraded batch reached the DW. We added the 0.1% floor and reran Tests A–E. Testing the gate is part of the system.

Honest story: when we first ran this test, the prepared gate only required “at least one match”, and the degraded batch got through. We added the 0.1% floor, justified by KPI-02 (genres need n ≥ 5), and reran every test. That is exactly what the test was for.

What the system can and cannot establish

Limitations

  • Winners only: no nominee tier in the source
  • Exact match: remasters, live versions and missing artists stay unmatched (4.1% of Grammy keys matched), measured every run
  • One popularity snapshot: association, not causal post-award effect
  • Small n in some genres: shown next to every value
  • Award years end in 2019

Next steps

  • Second-pass fuzzy match into a review queue, never straight into the DW
  • A nominee source to enable a winner / nominee / catalog tier
  • Scheduled runs with alerting on Critical failures
  • Unit tests for TR rules in CI

Backup · likely questions

Short answers to hard questions

Why are validation tasks not retried?

Data-quality failures are deterministic: the same batch reproduces the same violation. Retrying only delays the evidence (Tests B, E). Transient classes do retry (Test D).

Why not pass DataFrames through XCom?

XCom lives in the Airflow metadata DB and is meant for coordination. Tasks pass Parquet paths and small dicts; data is persisted per run for investigation.

Validation vs transformation?

Validation measures and records; transformation applies rules that stand on their own (TR-xx). We never change data to make a check pass. Values that cannot be repaired are dropped and counted, not imputed.

What if load_dw fails halfway?

One transaction: everything rolls back, and the previous snapshot stays. The retry or the next run converges because the load is idempotent.

Why a LEFT join and many-to-one?

Non-awarded tracks are the comparison group. Aggregating Grammy rows per key first makes duplicate matches impossible, and validate="many_to_one" enforces it.

How did you pick thresholds?

From profiling and the requirement they protect: e.g. duration ≥ 99.9% tolerates one corrupted row but stops a systemic error; match rate ≤ 5% flags a key that became too loose.

Why is coverage so low? Is the integration wrong?

The prepared gate checks the integration is coherent (PREP-06) and has a minimum match rate (PREP-07, proven in Test E). Low coverage is structural (38% without artist, non-song categories), and it is measured every run.

Why PostgreSQL and not SQLite?

The brief forbids SQLite. PostgreSQL gives transactions, ON CONFLICT upserts, CHECK constraints and concurrent access for Airflow, Metabase and the pipeline.
