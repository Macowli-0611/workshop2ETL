“We built a reliable batch pipeline that joins the Spotify catalog (a CSV) with the Grammy Awards (extracted from a PostgreSQL source database) into a star-schema Data Warehouse and a dashboard with three KPIs.”

Key message: a system, not a script. Failures are anticipated (rules with severities), controlled (gates block the load) and observable (states, logs and per-run evidence).

Three questions that need both sources

Spotify knows how music sounds and how popular it is. The Grammys know what was awarded.

The brief asks for requirements before profiling and modelling. Every requirement combines one attribute that only Spotify has (sound, popularity, genre, explicit, credits) with one that only the Grammys have (winner, year).

If asked “why no nominees?” The Grammy file only contains winners (4,810 of 4,810), so we compare winners vs the rest of the catalog.

32 expectations implement 18 rules (13 Critical, 3 Warning, 2 Informational). Coverage follows the risks, not a fixed number per dataset.

Thresholds are decisions: duration > 1,000 ms in 99.9% of rows tolerates the single corrupted row but stops a systematic error; matched rows must be at least 0.1% of the catalog, because below that KPI-02 has no comparable genre.

Trap: “Do you change data so validation passes?” No. Validation detects; transformation applies rules justified on their own.

For each gate: the batch (this run's staging file) plus an Expectation Suite form a Validation Definition; a Checkpoint runs it; our policy reads the severities and decides STOP, CONTINUE_WITH_WARNING or CONTINUE.

The result is per-rule evidence, not a Boolean. Suites, validation definitions and checkpoints are exported to gx/ on every run.

If asked “why an ephemeral context?” The two raw gates run in parallel; a shared file context would be written by two processes at once.

114,000 − 1 corrupted − 450 duplicates = 113,549 prepared rows = 113,549 fact rows. Every number comes from the run's integration_report.json.

Integration contract: LEFT join from the catalog (non-awarded tracks are the comparison group), key = normalized title + primary artist, many-to-one enforced by pandas (validate="many_to_one"). Unmatched Grammy keys (95.9%) are measured: many categories are not songs and 38% have no artist.

If asked “why no fuzzy matching?” It creates false positives that cannot be audited; we prefer an exact match on a normalized key and measure coverage.

Business process: a track's performance in its genre, enriched with its Grammy recognition. Unmatched tracks use default members (key 0), so there are no NULL foreign keys. CHECK constraints mirror the GX ranges.

Track-level KPIs collapse genres first, so a song that appears in several genres counts once.

The highest-weighted criterion (0.90). There is no blanket retries=3: the default is 0 and each task opts in by failure class. Test D proves the transient case; Tests B and E prove the deterministic case.

Every task log starts with BATCH CONTEXT (run id, task, try), so we can say what ran, when, where it failed, why, and what happened next.

Strategy: snapshot load = upsert on the declared grain plus a purge of rows that are not in the current batch, in one transaction. Rerun result: 0 inserted, 113,549 updated, 0 purged; counts and measures identical; only batch_id changes.

Partial failure? Everything runs in one transaction, so any error rolls back dimensions and facts together and the previous snapshot stays. A failure before the load (Tests B, E) never touches the DW.

The brief asks for proof that load_dw is gated by the prepared gate. We appended a suffix to every Grammy artist credit: year, nominee, schema and volume stay valid, so both raw gates pass, but almost no key matches (475 → 71 rows) and the prepared gate stops the batch.

Honest story: the first time we ran this test, the gate only required “at least one match” and the degraded batch got through. We added the 0.1% floor (justified by KPI-02 needing genres with n ≥ 5) and reran every test.

Looker Studio reads the KPI views of the Data Warehouse, never a CSV. Because Looker runs on Google's servers, publish_dw.py copies the DW to a cloud PostgreSQL after each load (one transaction, reconciled with the local DW), and Looker logs in with a role that can only read the views.

Findings: winners score 45.21 vs 33.17 in popularity, with higher valence and lower acousticness; soul, jazz and country show the largest uplift, pop and electro are negative; explicit winners rise 0% → 7.3% → 14.1% → 20.2%, collaborations reach 35.7% in the 2010s. Association, not causation; n is shown because some genres are small.

Questions

Why are validation tasks not retried?

Data-quality failures are deterministic: the same batch fails the same way (Tests B, E). Transient failures do retry (Test D).

Why not pass DataFrames through XCom?

XCom lives in the Airflow metadata DB. Tasks pass file paths; data is kept per run for investigation.

What if load_dw fails halfway?

One transaction: everything rolls back and the previous snapshot stays. The retry converges because the load is idempotent.

Why a LEFT join, many-to-one?

Non-awarded tracks are the comparison group. Grammy rows are aggregated per key first, so a catalog row matches one record at most.

How did you choose thresholds?

From profiling and the requirement they protect, not from what the current batch passes.

Why a cloud copy for the dashboard?

Looker Studio cannot reach localhost. The published copy is reconciled with the DW and read through a views-only role.
